# LLM 모델 비교·선정 보고서

## 1. 비교 목적
기능 요구사항(회원가입) 기반 테스트 케이스 생성 어시스턴트 과업을 수행함에 있어, 서로 다른 3종의 대규모 언어 모델(LLM)인 GPT-5 mini, Gemini 3 Flash, Claude Haiku 4.5의 테스트 케이스 설계 능력, 프롬프트 준수율 및 명세 기반 사고 능력을 비교·평가하여 업무 자동화에 가장 적합한 최적의 모델을 선정하는 것을 목적으로 합니다.

## 2. 비교에 사용한 동일 입력 (테스트 프롬프트)

### [v1 프롬프트 (일반 지시)]
```jsx
아래 기능 요구사항을 분석하여 테스트 케이스를 생성해줘.
기능명: 회원가입

요구사항:
- 이메일 필수
- 이메일 중복 불가
- 비밀번호 8~20자
- 닉네임 2~10자
```

### [v1.5 프롬프트 (단계적 접근 및 작성 규칙 지정)]
```jsx
당신은 백엔드 QA 테스트 설계 전문가다.

아래 기능 요구사항을 분석하여 테스트 케이스를 생성한다.

작성 규칙:
1. 요구사항에 명시된 내용은 테스트 케이스로 작성한다.
2. 요구사항에 없지만 테스트에 영향을 주는 정책은 임의로 확정하지 말고 "확인 필요 사항"으로 분리한다.
3. 테스트 케이스는 정상 케이스, 예외 케이스, 경계값 테스트, 데이터 정합성 테스트, 보안/권한 테스트로 분류한다.
4. 각 테스트 케이스는 TC-ID, 분류, 시나리오, 전제조건, 입력값, 예상 결과, 우선순위 형식으로 작성한다.
5. 비밀번호 8~20자, 닉네임 2~10자처럼 범위 조건이 있으면 최소값-1, 최소값, 최대값, 최대값+1을 반드시 포함한다.
6. 이메일 중복처럼 데이터 정합성과 관련된 요구사항은 중복 데이터, 동시 요청 가능성을 고려한다.
7. 최종 출력에는 불필요한 칭찬, 설명, 감탄문을 포함하지 않는다.

기능명: 회원가입

요구사항:
- 이메일 필수
- 이메일 중복 불가
- 비밀번호 8~20자
- 닉네임 2~10자
```

## 4. 모델별 결과 요약 및 특징 분석

### 4.1 모델별 특징
* **GPT-5 mini**
  * **장점**: 요구사항 기반 경계값 분석이 완전하고 예외 상황 고려가 훌륭하며 동시성까지 포함됨. 명세 기반 사고 및 정책 추정이 최소화되어 있으며 확인 필요 사항 분리가 우수하고 정합성 관점이 강함.
  * **단점**: 과도하게 상세하여 요구사항 밖의 테스트가 많으며, 일부 케이스는 API 설계 리뷰 수준으로 확장됨 (예: Rate Limit, CAPTCHA, 요청 크기 제한 등 회원가입 기능 범위를 일부 넘어섬).
* **Gemini Flash**
  * **장점**: 가장 간결하며 실무에서 바로 사용할 수 있는 형태를 띠고 보안 테스트를 포함함.
  * **단점**: 경계값 성공 케이스(8자, 20자, 2자, 10자) 누락이 발생함. HTTP 상태코드, 해시 저장 여부, 이메일 형식 미검증 정책 등을 독자적으로 확정하여 QA 관점보다 개발자 관점의 가정이 많음.
* **Claude Haiku 4.5**
  * **장점**: 테스트 분류가 깔끔하고 BVA(경계값 분석) 적용이 우수하며 정합성 및 보안 테스트가 충실함.
  * **단점**: 실제 입력 데이터가 부족하고 실무성 있는 예외 상황이 부족함. 요구사항에 없는 이메일 형식 오류 메시지(TC-013)나 비밀번호 암호화 저장(TC-018), SQL Injection(TC-019), XSS(TC-020) 등 요구사항 외 정책 가정을 사실상 확정하여 프롬프트 규칙 위반이 가장 많은 편임.

| --- | --- | --- | --- |

### 4.3 Few-shot 및 검증 전략 적용 전/후 비교 분석

Few-shot 예시 3종과 환각 방지 검증 전략을 도입하기 전(v1.5)과 도입한 후(v2)의 모델별 실행 결과 비교 및 그 근거는 다음과 같습니다.

#### 1) Few-shot 적용 전 (v1.5 프롬프트)
* **공통 문제점**: 작성 규칙과 구조 지시만 제공되고 구체적인 예시(Few-shot)가 없어, 모델이 명세에 없는 내용을 자의적으로 추정하여 채워 넣는 환각 현상과 모호한 조건에서의 가상의 케이스 폭주가 발생했습니다.
* **모델별 동작 및 근거 바로가기**:
  * **Gemini Flash** ([v1.5 출력 원본 바로가기](#b2-gemini-3-flash-v15)): 비밀번호/닉네임의 최소·최대 성공 경계값을 누락하고, 요구사항에 없는 HTTP 상태코드(`201 Created`, `400 Bad Request`, `409 Conflict`) 정책을 자의적으로 확정하여 기재함.
  * **Claude Haiku 4.5** ([v1.5 출력 원본 바로가기](#b3-claude-haiku-45-v15)): SQL Injection, XSS, 이메일 형식 등 요구사항 외 정책 가정을 사실상 확정 지음.
  * **GPT-5 mini** ([v1.5 출력 원본 바로가기](#b1-gpt-5-mini-v15)): 가장 훌륭한 수준이었으나 동시성 처리 등 일부 영역에서 명세 외 가정이 일부 섞임.

#### 2) Few-shot 및 검증 전략 적용 후 (v2 프롬프트)
* **공통 개선점**: Few-shot 예시 3종(정상/경계값, 데이터 정합성/동시성, 모호한 입력 보류)과 환각 방지 지침이 추가되어, 모델이 임의 정책 판단을 유보하고 플레이스홀더를 사용하거나 생성을 보류하는 안전 장치가 정상 작동했습니다.
* **모델별 동작 및 근거 바로가기**:
  * **Gemini Flash & Claude Haiku 4.5** ([v2 출력 원본 바로가기](#c1-gemini--claude-v2)): 이전 버전의 상태코드 및 암호화 방식 임의 확정(환각) 현상이 100% 통제됨. 명세 외 항목을 **`[확인 필요] 사후 정책 결정에 따름`** 플레이스홀더로 안정적으로 치환했으며, 13개 케이스를 규칙에 맞춰 온전히 구조화함.
  * **GPT-5 mini** ([v2 출력 원본 바로가기](#c2-gpt-v2)): 이전의 풍부한 케이스 도출 능력을 유지하며, 이메일 유효성, 비밀번호 복잡성 등 **총 13가지의 확인 필요 사항**을 정밀하게 추출함. `[확인 필요]` 플레이스홀더 규칙을 준수하여 환각이 발생하지 않았음.

## 5. 최종 선정 결론
v1.5 및 최종 v2 프롬프트 적용 결과, 세 모델 모두 v1에 비해 출력 형식 준수율과 테스트 분류 품질이 크게 개선되었습니다. 특히 최종 v2 프롬프트에서는 Few-shot 예시와 환각 방지 검증 전략이 적용되어, 이전 버전(v1.5)에서 발생하던 Gemini Flash와 Claude Haiku 4.5의 HTTP 상태코드 및 암호화 방식 환각 오류가 해결되었습니다. 세 모델 모두 미지정 정책 영역에 대해 `[확인 필요]` 플레이스홀더를 적용하며 명세 기반 테스트 설계 규칙을 성실히 준수하였습니다.

또한, 동일한 프롬프트 상에서 모델이 인식하는 토큰 수와 cache 여부를 정확히 측정하지 않아 정확하진 않지만, 단순 가격면에서 비교한 결과 GPT-5 mini의 모델 토큰이 가장 저렴하다는 가격적 이점이 있습니다.

따라서 확인 필요 사항 식별 깊이와 엣지 케이스 도출 수준에서 완성도와 비용을 고려한 결과 **GPT-5 mini**를 최종 업무 자동화 모델로 선정합니다.

## 5. 시스템 프롬프트 (최종 v2 전문)
```
당신은 백엔드 QA 테스트 설계 전문가다.

아래 기능 요구사항을 분석하여 테스트 케이스를 생성한다.

작성 규칙:
1. 요구사항에 명시된 내용은 테스트 케이스로 작성한다.
2. 요구사항에 없지만 테스트에 영향을 주는 정책은 임의로 확정하지 말고 "확인 필요 사항"으로 분리한다. 특히 요구사항이 한 줄 이하이거나 비즈니스 정책이 전혀 없어 모호한 경우, 임의로 테스트 케이스를 생성하지 않고 Few-shot 예시 3처럼 상세 질문만 던진 후 상세 테스트 케이스 생성을 대기(보류)한다.

4. 각 테스트 케이스는 TC-ID, 분류, 시나리오, 전제조건, 입력값, 예상 결과, 우선순위 형식으로 작성한다.

[검증 전략 (환각 방지)]
```

## 6. Few-shot
본 시스템은 정밀한 테스트 시나리오 작성을 유도하기 위해 다음과 같이 3종류의 Few-shot 예시를 시스템 지침에 내재화했습니다.
1. **정상 및 경계값/예외 처리 예시**: 경계값(최소-1, 최소, 최대, 최대+1) 검증 논리를 구체화하고 정상/예외 흐름을 처리하는 정형적인 예시 (예시: 로그인)
2. **데이터 정합성 및 동시성 예시**: 중복성 검증 시 동시 요청에 따른 데이터 정합성 및 경쟁 조건을 테스트 시나리오로 명시하는 법에 대한 예시 (예시: 닉네임 변경)
3. **모호한 입력 예시**: 명세 요구사항이 부족할 때 AI가 임의로 정책을 확정(환각)하지 않고, 사용자에게 질문을 던지며 작성을 보류하는 엣지 케이스 예시 (예시: 회원 탈퇴)

## 7. 환각 검증 설계
AI가 요구사항 명세서 외의 기획을 임의로 결정(환각 현상)하는 것을 방지하기 위해 다음과 같은 검증 필터를 내재화하여 설계했습니다.
* **불명확성 분리 원칙**: 명세서에 구체적으로 기재되지 않은 항목(예: HTTP 상태코드 규약, 에러 메시지 텍스트, 비밀번호 해싱 방식 등)은 AI가 자의적으로 예상 결과에 포함하지 못하도록 규칙화했습니다.
* **확인 필요 사항 바인딩**: 불명확한 부분들은 항상 '확인 필요 사항' 섹션으로 질문 리스트화하여 사용자에게 사후 확인을 받도록 유도하고, 관련 테스트 케이스의 예상 결과는 사후 정책 결정에 따르도록 표시(플레이스홀더)하여 환각 발생에 대비하였습니다.

### 8.2 개선 사유
* **v1 → v1.5 개선 사유**:
  * v1은 단순 기능 요구사항에 테스트 케이스 생성만을 요청하여 모델마다 출력 형식과 기준이 달랐으며, 명세에 없는 이메일 형식이나 공백 처리를 임의로 가정하는 단점이 있었습니다.
  * 이를 개선하기 위해 v1.5에서는 작성 규격(TC-ID, 분류, 시나리오 등)과 분류 기준을 명시하고 경계값(최소-1, 최소, 최대, 최대+1) 및 데이터 정합성 처리를 강제하며, 요구사항 외의 가정을 "확인 필요 사항"으로 분리하도록 명시하였습니다.
* **v1.5 → v2 개선 사유**:
  * v1.5의 단순 규칙 명시만으로는 AI가 실제 입력 데이터를 추론하거나 모호한 입력을 만났을 때 규칙을 어기고 임의로 가정을 기재하는 한계가 여전히 존재했습니다.
  * 이를 개선하기 위해 v2에서는 구체적인 예외 케이스와 동시성 테스트 작성을 명시해 주는 **Few-shot 예시 3종**을 추가했습니다. 특히 그중 1종은 요구사항이 매우 모호할 때 AI가 즉시 테스트 케이스를 생성하지 않고 되묻기 위한 확인 사항을 정리하는 예시로 구성했습니다.
