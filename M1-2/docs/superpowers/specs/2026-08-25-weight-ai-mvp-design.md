# 개인 체중 변화 기록 분석 AI MVP 설계

## 1. 목적과 범위

날짜와 체중으로 구성된 개인 시계열 데이터를 Firestore에 저장하고, 사용자가 데이터 CRUD와 AI 채팅을 한 화면에서 사용할 수 있는 웹 서비스를 만든다. AI는 전체 요약을 기본 컨텍스트로 받고, 특정 날짜와 기간에 대한 조회·분석은 Function Calling으로 수행한다.

보너스 범위 중 그래프, 데이터 내보내기, 다크 모드, MCP Server, GPT Actions 및 멀티채널 연동은 구현하지 않는다. Function Calling은 정확한 날짜·기간 조회를 위해서만 적용한다.

## 2. 확정된 선택

검토한 접근은 다음 세 가지다.

1. 모든 체중 데이터를 시스템 프롬프트에 포함한다. 구현은 단순하지만 데이터 증가에 따라 토큰 비용이 증가하고 기간 통계의 정확성이 모델에 의존한다.
2. 필수 FastAPI 엔드포인트와 읽기 전용 Function Calling이 공통 서비스 계층을 사용한다. 필수 요구사항을 충족하면서 조회와 계산을 백엔드가 담당한다.
3. AI가 CRUD까지 수행한다. 대화형 변경은 편리하지만 확인·취소·권한 설계가 추가되어 MVP 범위를 키운다.

두 번째 접근을 채택한다. 데이터 변경은 데이터 관리 화면에서만 수행하고, AI 도구는 조회와 분석만 허용한다.

## 3. 데이터 준비와 규칙

### 3.1 CSV 형식

```csv
date,value,memo
2025-01-01,72.4,
2025-01-03,72.1,
```

- `date`: `YYYY-MM-DD`
- `value`: kg 단위 숫자
- `memo`: 선택 문자열
- UTF-8 인코딩과 헤더를 사용한다.
- 날짜와 체중 중 하나라도 없는 행은 가져오기 전에 제외한다.
- 날짜별 기록은 한 건만 유지한다.
- 날짜 오름차순으로 정렬한다.
- 정제 후 유효 데이터는 100건 이상이어야 한다.

초기 데이터는 일회성 가져오기 스크립트로 Firestore에 등록한다. 웹에는 CSV 업로드 UI를 만들지 않는다.

### 3.2 Firestore `data` 문서

```json
{
  "date": "2025-01-01",
  "value": 72.4,
  "memo": "",
  "created_at": "server timestamp",
  "updated_at": "server timestamp"
}
```

검증 규칙은 다음과 같다.

- 미래 날짜를 허용하지 않는다.
- 체중은 20kg 이상 300kg 이하, 소수점 첫째 자리까지 허용한다.
- 메모는 최대 200자다.
- 동일 날짜의 중복 등록을 거부한다.
- 수정 시에도 날짜 중복을 검사한다.

### 3.3 결측치와 추세

결측 날짜를 임의로 보간하지 않는다. 기간, 개수, 평균, 최고, 최저와 추세는 날짜와 체중이 모두 유효한 기록만 사용한다.

최근 추세는 최근 10개 기록의 평균과 그 이전 10개 기록의 평균을 비교한다.

- 차이가 `-0.2kg` 미만이면 `감소`
- 차이가 `+0.2kg` 초과이면 `증가`
- 차이가 `-0.2kg` 이상 `+0.2kg` 이하이면 `유지`
- 유효 기록이 20건 미만이면 추세를 계산할 수 없음을 명시한다.

## 4. 시스템 구조

저장소는 `M1-2/backend`와 `M1-2/frontend`로 구성한다.

```text
Vanilla Frontend
    │
    ▼
FastAPI Routers
    │
    ├── Data Service ─────────── Firestore data
    ├── Conversation Service ─── Firestore conversations
    └── Chat Service
           │
           ├── Summary context injection
           ├── Function tool dispatcher
           └── OpenAI API
```

라우터는 HTTP 요청과 응답을 담당하고, 서비스는 검증 이후의 업무 규칙과 Firestore 접근을 담당한다. API 엔드포인트와 Function Calling 도구는 동일한 데이터 서비스를 호출하여 통계 계산을 중복하지 않는다.

## 5. 백엔드 API

### 5.1 데이터 API

- `POST /api/data`: 기록 추가
- `GET /api/data`: 전체 기록을 날짜 내림차순으로 조회
- `GET /api/data?start_date=...&end_date=...`: 선택 기간 조회
- `PUT /api/data/{id}`: 기록 수정
- `DELETE /api/data/{id}`: 기록 삭제
- `GET /api/data/summary`: 전체 요약 조회

기간 조회 규칙은 다음과 같다.

- 범위가 없으면 전체를 조회한다.
- 시작일만 있으면 해당 날짜 이후를 조회한다.
- 종료일만 있으면 해당 날짜 이전을 조회한다.
- 시작일이 종료일보다 늦으면 `400` 오류를 반환한다.
- MVP에서는 페이지네이션을 적용하지 않는다.

요약 응답에는 전체 기간, 유효 기록 수, 평균, 최고·최저 체중과 해당 날짜, 최초·최근 체중, 전체 변화량, 최근 두 구간 평균과 추세를 포함한다.

### 5.2 대화 API

- `POST /api/conversations`: 새 대화를 저장하거나 기존 대화에 메시지를 추가한다.
- `GET /api/conversations`: 제목과 최근 수정 시각을 포함한 목록을 반환한다.
- `GET /api/conversations/{id}`: 전체 메시지를 반환한다.
- `DELETE /api/conversations/{id}`: 대화를 삭제한다.

새 채팅에서 `conversation_id`를 생성하고 첫 질문을 제목으로 사용한다. 사용자 질문과 AI 답변은 한 문서의 `messages` 배열에 순서대로 저장한다.

### 5.3 채팅 API

- `POST /api/chat`: 사용자 질문과 선택적인 `conversation_id`를 받는다.

처리 순서는 다음과 같다.

1. 데이터 서비스에서 전체 요약을 조회한다.
2. 요약을 시스템 프롬프트에 삽입한다.
3. OpenAI API에 사용자 질문과 읽기 전용 도구 스키마를 전달한다.
4. 모델이 도구를 요청하면 백엔드가 해당 서비스 함수를 실행한다.
5. 도구 결과를 모델에 전달해 최종 답변을 생성한다.
6. 사용자 질문과 AI 답변을 대화 기록에 자동 저장한다.
7. 답변과 `conversation_id`를 반환한다.

모델명과 응답 길이 제한은 환경 변수로 관리한다. 시스템 프롬프트는 저장된 데이터만 근거로 답하고, 기록이 없는 날짜의 값을 추정하지 않으며, 의료 진단이나 치료 지시를 하지 않도록 제한한다.

## 6. Function Calling

AI가 사용할 수 있는 도구는 다음 네 개로 제한한다.

- `get_weight_summary()`: 전체 데이터 요약
- `get_weight_by_date(date)`: 특정 날짜 기록
- `get_weight_records(start_date, end_date)`: 특정 기간 기록 목록
- `get_weight_statistics(start_date, end_date)`: 특정 기간 평균·최고·최저·변화량

도구는 읽기 전용이다. 추가·수정·삭제 도구는 제공하지 않는다. 날짜에 기록이 없으면 명시적인 `not_found` 결과를 반환하고 모델이 값을 추정하지 못하게 한다.

## 7. 프론트엔드

HTML, CSS, JavaScript만 사용한 단일 페이지 대시보드로 구현한다.

- 왼쪽: 새 대화 버튼, 대화 목록, 대화 삭제
- 가운데: 메시지 목록, 질문 입력, 전송 버튼, 로딩 표시
- 오른쪽: 체중 요약, 데이터 입력 폼, 데이터 목록과 수정·삭제
- 모바일: 세 영역을 위아래로 재배치

데이터 추가·수정·삭제가 성공하면 목록과 요약을 다시 조회한다. 모든 비동기 작업은 로딩 상태와 성공 또는 오류 메시지를 표시한다. 삭제 작업은 실행 전에 확인한다.

## 8. 오류 처리

- Pydantic이 날짜, 체중과 메모를 검증한다.
- 중복 날짜는 `409`, 존재하지 않는 문서는 `404`, 잘못된 기간은 `400`으로 응답한다.
- Firestore와 OpenAI 오류는 내부 세부 정보나 키를 노출하지 않고 사용자용 메시지로 변환한다.
- OpenAI 호출 실패 시 실패한 AI 답변을 대화 기록에 저장하지 않는다.
- Function Calling의 이름과 인자를 허용 목록 및 Pydantic 모델로 재검증한다.
- Render 콜드스타트가 발생할 수 있음을 채팅 로딩 안내에 표시한다.

## 9. 환경 변수와 배포

백엔드 환경 변수 최소 세트는 다음과 같다.

- `OPENAI_API_KEY`
- `OPENAI_MODEL`
- `OPENAI_MAX_OUTPUT_TOKENS`
- `FIREBASE_SERVICE_ACCOUNT_JSON`
- `ALLOWED_ORIGINS`

프론트는 백엔드의 `API_BASE_URL`을 환경별 설정으로 주입받는다. 서비스 계정과 API 키는 저장소에 커밋하지 않는다.

- Render: `M1-2/backend`의 FastAPI 애플리케이션 배포
- Vercel: `M1-2/frontend` 정적 사이트 배포
- CORS: 로컬 프론트 주소와 실제 Vercel 도메인만 허용
- Swagger UI: Render 배포 주소의 `/docs`에서 확인

## 10. 테스트와 완료 기준

### 백엔드 테스트

- 데이터 검증, 중복 날짜와 결측치 처리
- CRUD 성공 및 오류 응답
- 전체·부분 기간 조회
- 요약 통계와 추세 경계값
- 대화 생성·추가·조회·삭제
- Function Calling 라우팅, 인자 검증과 도구 결과 전달
- OpenAI 실패 시 대화 미저장

Firestore와 OpenAI는 테스트 대역으로 교체해 단위 테스트에서 외부 비용과 네트워크 의존성을 제거한다.

### 수동 확인

- 로컬 프론트와 백엔드 연동
- Swagger에서 모든 필수 API 실행
- 체중 CRUD 후 목록과 요약 자동 갱신
- 특정 날짜, 기간 기록, 기간 통계 질문
- 대화 자동 저장, 목록 조회와 불러오기
- Render와 Vercel 배포 URL 접속
- README의 로컬 실행 및 환경 변수 절차 재현

### 제출 증거

- 데이터 요약이 표시된 채팅 질문·답변 화면
- 추가·수정·삭제 중 동작이 드러나는 데이터 관리 화면
- 저장된 대화를 불러온 대화 기록 화면
- 프론트, 백엔드 API와 Swagger 배포 URL
